页面结构

第二列「原型定位」：在话题广场 HTML 里对应哪一块，主要写类名、层级（方便和 topics.html 对照改样式、接数据）；不是给用户看的产品文案。

区域原型定位（类名与层级）内容与规则
面包屑main.app-main > .crumb首页 → 发现 → 热门话题
Hero 汇总 .topic-hero 标题 + 副文案
.hero-stats 四格 .hs:nth-child(1..4) > .v

上线：下面每一格数字都由后台按规则实时统计，接口「话题汇总统计」返回后写入页面，不能在页面里写死。 共用说法（全文统一）：
· 有效话题：符合 §1.3 的话题（已发布、未下架、用户看得见、审核通过等），同一个话题只算一次。
· 本周：北京时间，从本周一 0 点起，到下周周一 0 点止（与排行榜一致）。
· 今天：北京时间当天 0 点到次日 0 点。
四指标细则见上表。

页面展示统计时间范围怎么算（通俗说明）
正在燃起的 话题个数 当前时刻 数一数：全站现在有多少个有效话题。老话题只要仍有效就算，和本周有没有新帖无关。这个数字和下面四格不是同一个含义。
本周活跃话题 本周 在有效话题里，再数：本周有没有「动静」。满足任一即可算活跃：
① 本周有人在该话题下发了新帖（已公开发布）；或
② 本周在该话题下有过互动：有人点赞、评论、转发，或进入绑定了该话题的直播间（新发帖已在 ① 里）。
结果：满足 ① 或 ② 的话题各算 1 个，最后数一共有多少个。只有浏览、本周既没发帖也没互动的话题不算活跃。
今日新增帖子 今天 数一数：今天新发布、且至少带一个有效话题标签的帖子有多少条。只算公开发布的帖；一条帖即使打了多个话题标签，也只算一条。进行中的直播场次不算在这里。
本周参与人次 本周 数一数：本周在有效话题下发生了多少次「参与行为」（不是去重人数）。
· 互动类（点赞、评论、转发、带话题发帖、进直播间等）：用户每做一次算 1 次，同一人做 10 次就算 10 次。
· 浏览类（打开话题页、在话题下刷帖等）：同一人、同一话题、同一天里无论打开多少次，最多只计 1 次，用来防刷。
与排行榜排序用的「本周互动次数」不是同一个指标（口径见 §1.1），这里按上面规则纯累加次数。
直播中 打开页面这一刻 数一数：此刻正在直播、且至少关联一个有效话题的直播间有多少间。已下播的不算；一间房绑多个话题仍算一间。不是本周开播总场次，会随时间变。
排行前50名的话题main.app-main > h3 小节标题 + .tp-leaderboard（H5：.h5-sec-title + .h5-tp-leaderboard）纵向列表 .tp-lb-row / .h5-lb-row：仅展示本周排序第 1～50 名；每行名次、# 话题名、.tp-lb-stats（帖 / 浏览 / 创作者）、.tp-lb-grow。名次样式见 §1.2
列表续载#tpLbSentinel + #tpLbLoadMore上线：首批一页（如 20 条）；滚到底或点按钮加载下一页直到第 50 名。原型：共 50 条——首屏 5 条 + 隐藏 45 条（.is-lazy-hidden），每批 5、可懒加载 9 次 后显示「已加载全部话题」

1.1 排行前50名的话题 · 排序逻辑

产品规则：广场主区只有一条列表（.tp-leaderboard），标题为「排行前50名的话题」。按 §1.1 算出完整序后，只展示前 50 名（rank 1～50），第 51 名及以后不在本页出现。首屏先出一页，之后通过滚到底或点「加载更多话题」懒加载下一页，直到第 50 名。第 1～3 名、第 4～10 名用更醒目的名次样式（§1.2），11～50 为普通序号。

统计时间：与全文「本周」一致（北京时间周一 0 点～下周一 0 点）；若全站改用「滚动近 7 天」，排行榜与 Hero 须同一口径。

先算每个有效话题在本周的三项数（只统计挂在该话题下、且发生在本周内的事件）：
· 互动次数：点赞、评论、转发、新发帖、进入绑该话题的直播间——每发生一次计 1 次（同一人重复操作也计多次；不算纯打开话题页、刷列表的浏览）。
· 有效发帖数（列表「N 帖」、排名第二 tie-break）：见 §1.2「有效发帖数怎么数」。
· 浏览人数：打开该话题页或话题下帖子详情的人数，按用户去重。
怎么排名（不用配分值、不用加权公式）：
1. 先看互动次数，多的靠前；
2. 一样多，比有效发帖数；
3. 还一样，比浏览人数。
排好序后取前 50 名进入本页列表（rank 1～50）。接口按分页返回这 50 条，前端按 rank 顺序拼接并懒加载至第 50 名。

每行展示的「18.6K 帖」「4.2M 浏览」同属本周：帖数 = 有效发帖数；浏览 = 本周话题页 + 帖详情浏览量（次数或去重，全站统一）。原型 HTML 共 50 行，与 topics.html 一致。

接口对照：分页排行榜（cursor/offset + pageSize），每条含 rank、话题名、本周互动次数、有效发帖数、浏览人数、本周创作者数、趋势%、算数时间；另有 hasMore 或 total（字段名研发自定）。

1.1.1 「+186% / +98%」· 趋势百分比（.tp-lb-grow）

排行榜每一行右侧的「+百分之几」为同一套趋势。

「核心量」是什么、怎么算：就是该话题的互动次数（§1.1 排名比大小的第一项），算法如下——在对应时间窗口内，挂在该话题下且计入互动的事件：点赞、评论、转发、新发帖、进入绑该话题的直播间，每发生一次计 1（同一人重复也算）。新发一条带该话题的帖 = 计 1 次互动，发帖已经算在里面，不会少算。
趋势用的核心量不单独改用「有效发帖数」「浏览人数」那两个排序辅助项（避免和互动次数各算各的、口径打架）；不计纯浏览（打开话题页、刷列表）；不做加权。
趋势怎么算：
1. 先算该话题本周窗口内的互动次数（即本周核心量）。
2. 再算上周等长窗口内的互动次数（上周核心量）。
3. 若上周核心量为 0，按产品约定处理（建议视为大幅涨或显示「—」）。
4. 算「涨了多少」：用本周核心量减去上周核心量，再除以上周核心量，得到比例后换成百分数（上周几乎是 0 时，除数按 1 处理，避免算不出来）。
5. 展示规则（对称阈值约 ±5%）：
· 涨幅 > 约 5%：.tp-lb-grow.is-up，上箭头 + 「+整数%」（上限建议 999%）；
· 跌幅 > 约 5%：.tp-lb-grow.is-down，下箭头 + 「-整数%」；
· 涨跌均在约 ±5% 内：.tp-lb-grow.is-flat，文案「持平」（无箭头或横线 icon）；
· 也可按产品选择「几乎不动」时不展示该格。

举例（Apex +98%）：上周互动次数一千，本周一千九百八十，相当于在上周基础上涨了约九成八，页面上写 +98%。

原型：数字手写；榜内样例含涨（多数行）、第 49 名 -8%、第 50 名 持平；上线由统计任务定时刷新。

1.2 排行榜列表 · .tp-leaderboard 展示

布局：单列列表，一行一个话题（Web .tp-lb-row，H5 .h5-lb-row）。共 50 行（本周前 50 名），靠懒加载分批出现在页面上。

名次样式（左侧 .tp-lb-rank）：
· 第 1～3 名：华丽图标位——金/银/铜渐变底 + 图标（原型：皇冠、奖牌、奖杯）。
· 第 4～10 名：华丽数字位——品牌渐变底 + 两位序号（04～10）。
· 第 11 名及以后：统一样式——描边方框 + 普通序号（11、12…），无渐变。
上线时由接口字段 rank 决定用哪套样式；前端按 rank 数值切换 class（rank-1|2|3、rank-top、rank-plain）。
懒加载（两种触发，逻辑相同）：
① 滚动：用户用滚轮或触控把列表滚到接近底部（监听底部哨兵 #tpLbSentinel 进入视口）→ 请求并追加下一页；
② 点击：点「加载更多话题」按钮（#tpLbLoadMore）→ 同样追加下一页。
打开页面先请求第 1 页（如 rank 1～20）；重复上述触发直到没有更多或 rank 已到 N。rank 连续不重复。名次样式按全局 rank（1～3 图标、4～10 华丽数字、11+ 普通框）。加载中应防重复请求。

有效发帖数怎么数（单话题 · 列表「N 帖」· 排名 tie-break）

统计窗口：与 §1.1 相同，默认本周（北京时间周一 0 点～下周一 0 点）。
计数对象：在该话题下、且同时满足下面条件的帖子，每条计 1：
① 在窗口内首次公开发布（不是草稿、不是定时未到点）；
② 当前对用户可见（与全站帖子可见规则一致）；
③ 至少关联一个有效话题（§1.3），且关联关系里包含本话题；
④ 同一条帖子打了多个话题标签，在本话题下仍只计 1 条；
⑤ 纯「正在直播」场次若不算帖子类型，则不计入（与 Hero「今日新增帖子」一致）。
展示：列表行 .tp-lb-stats 里的「N 帖」用该数。

单行字段（.tp-lb-row）：

页面上看到数据从哪来
左：名次 ICON / 数字接口 rank；样式规则见上（1～3 图标，4～10 华丽数字，11+ 普通数字）
「# 话题名」话题名称
18.6K 帖 · 4.2M 浏览 · 1.8K 创作者本周有效发帖数、本周浏览量、本周参与创作者数（去重）；文案统一，不用「主播开播」等异化说法
右：+186%§1.1.1 趋势百分比

原型：HTML 共 50 行（rank 1～50），首屏 5 行；6～10 为 rank-top，11～50 为 rank-plain；每批懒加载 5 行。

1.3 有效话题 · 定义与计数（Hero 标题「话题个数」）

标题里的话题个数 = 全站当前算数进有效话题的有多少个。与用户能点进详情、能在广场被发现一致。和 Hero 四格里的「本周活跃话题」不是一回事：老话题本周没动静仍可能有效；已下架/未过审的即使本周有帖也不算有效。

1.3.1 什么算「有效」（须同时满足）

序号条件说明
1已发布不是草稿、不是创建到一半；运营创建的官方话题也要正式发布后才有效
2未下架运营下架、违规下架、删号连带隐藏等 → 无效
3对用户可见广场/搜索等场景下普通用户能发现；仅链接可见、仅粉丝、仅内部测试 → 无效
4审核通过待审核、已驳回 → 无效；审核通过后再计入有效话题
5未合并到别的话题重复话题合并后，只保留主话题一条，从话题不再单独计数

1.3.2 什么不算有效（任一命中即排除）

场景处理
草稿、定时发布未到点不计入标题「话题个数」；到点发布后下一统计周期计入
地域/年龄策略不可见（用户未登录时用默认策略）全站话题个数按默认可见集统计，不按单个用户个性化缩小（避免每人标题数字不同）
仅搜索可见、广场列表故意不展示若产品允许「能搜不能上广场」，需单独配置；一期建议：只要公开且审核通过就算有效（与能否上列表无关）
测试 / 内部话题一律无效
软删除、封禁账号名下且无迁移无效

1.3.3 怎么数「话题个数」

逻辑：在数据库里找出同时满足 §1.3.1 全部条件的话题，每个话题 ID 只计一次，得到的总数就是标题上的「话题个数」。
与话题列表、分页用的「可展示话题」过滤条件必须一致，避免标题写 400、列表却只有 350 的矛盾。
结果可缓存 1～5 分钟；有话题上架、下架、审核通过时刷新缓存。

接口对照：话题汇总统计接口返回「有效话题总数」等字段（研发自定英文字段名）。

1.3.4 标题上数字怎么展示

真实个数页面上怎么写
不到 100写准确数字，如「9 话题」
100～999可向下取整到十位并加「+」，如 367 展示「360+」（表示至少这么多）
1000 及以上可向下取整到百位并加「+」，如 1840 展示「1800+」

原型脚本 topics-hero.js 仅对榜单行个数做上述格式化；上线后个数来自接口，格式规则不变。

本话题创作者 TOP · 帖数 / 互动量（侧栏 .creator-row .s）

统计窗口：与话题广场一致，默认本周（北京时间周一 0 点～下周一 0 点）；与 Hero「18,624 帖」等同窗口，除非产品单独定义「累计」入口（本页 Hero 带「本周 TOP」时不使用全站累计）。
帖数（如「42 帖」）：在该窗口内，创作者 U 在本话题 T 下的有效发帖数——规则同 §1.2「有效发帖数怎么数」：每条满足可见、已发布、关联 T 的帖子计 1，同帖多标签在 T 下仍计 1；纯直播场次不计入帖数。
公式：帖数(U,T) = COUNT(帖子 P | P.creator=U ∧ P 关联话题 T ∧ P 满足 §1.2 有效帖条件)
互动量（如「12.6K 互动」）：在同一窗口内，仅统计上述有效帖（及可选：绑定话题 T 且主播为 U 的进行中/已结束直播，若产品把进房计互动）上发生的互动次数，与 §1.1.1 核心量一致：点赞、评论、转发、进绑定该话题的直播间等各计 1 次（同用户重复操作仍计，除非产品去重）。
公式：互动量(U,T) = Σ 互动事件 e（e 归属 U 的内容且归属话题 T，且 e 类型 ∈ 互动类型集合）
排行：在本话题下对所有创作者按互动量降序（tie-break 可用帖数、再创作者 id）；取前 N 名展示（Web 原型 N=4，H5 样例 N=2）。
展示：互动量可 K/M 缩写（12.6K）；帖数为整数 +「帖」。

侧栏「话题热度趋势」· 曲线

展示什么：Web 侧栏卡片「话题热度趋势」——折线 + 下方横轴日期（原型为 4/19～今天），用形状表达话题 T 在一段时间内热不热、往哪走；无额外摘要文案条。
纵轴（上线）：按自然日汇总话题 T 的互动次数（与 §1.1.1 核心量同口径：赞、评、转、新帖、进绑定 T 的直播等，各计 1）。常用近 7～30 天 各一个点，连成折线；Y 轴可线性刻度或自适应，产品统一即可。
读图：点越高 = 当日互动越多；线往上 = 近期变热，往下 = 变冷。Hero / 广场上的「+186%」是周环比一个数，不在侧栏重复展示；若要与曲线互证，用户自行对比最近 7 天斜率与 §1.1.1 即可。
原型：SVG 折线与填充区为固定装饰，未绑定接口序列；横轴日期手写。H5 详情无此卡片。
